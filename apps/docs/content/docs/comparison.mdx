# Architectural Comparison & Technical Approaches

Building a scalable OCPP Central System (CSMS) or Station Client involves navigating multiple architectural decisions: type safety, schema validation, horizontal clustering, smart charging algorithms, framework integration (NestJS, Express), and protocol translation.

The **ocpp-ws-io ecosystem** was engineered from the ground up to solve these challenges natively in TypeScript. Below is a technical breakdown examining different architectural approaches across Node.js tools, legacy packages, and turnkey CSMS platforms like **CitrineOS**.

## 2. Comparing Architectural Models: `CitrineOS` (LF Energy / S44)

**CitrineOS** is an open-source Charging Station Management System hosted under LF Energy (Linux Foundation Energy).

### CitrineOS Design
- **Platform Stack**: Built as a comprehensive, standalone CSMS platform.
- **Infrastructure**: Operates with PostgreSQL (with PostGIS), RabbitMQ message broker, and Hasura GraphQL services.
- **Focus**: Turnkey network operations, NEVI compliance goals, and pre-configured device schemas.

### `ocpp-ws-io` Design
- **Embeddable Toolkit**: Built as an unopinionated, modular library suite. You install `npm install ocpp-ws-io` into your existing application or microservice architecture.
- **Framework Integration**: Native `@OcppGateway` decorators for NestJS, Express, Fastify, and Hono, allowing WebSocket upgrade routes to live directly alongside your existing REST APIs on the same port.
- **Database Freedom**: Zero mandated database schema or external message brokers; works with Prisma, Drizzle, TypeORM, MongoDB, or pure in-memory stores.
- **Protocol Translation Layer**: `ocpp-ws-io/proxy` bridges legacy OCPP 1.6 stations to OCPP 2.1 systems dynamically on the wire.

## 3. Comparing with `ocpp-rpc` & `node-ocpp`

Early Node.js projects often relied on packages titled `ocpp-rpc` or `node-ocpp`.

### Context
- Many of these repositories were designed during the early OCPP 1.6 days and have since become unmaintained or archived.
- They lack modern TypeScript typings, often rely on permissive `any` types, and do not validate payloads against official Open Charge Alliance (OCA) schemas.

### `ocpp-ws-io` Approach
- **Official OCA Schema Validation**: Every message payload is validated at the WebSocket boundary using Ajv and official OCA JSON Schemas. Malformed packets automatically return spec-compliant `FormatViolation` CallErrors before hitting application logic.
- **OCPP 2.0.1 and 2.1 Ready**: Native support for modern EV charging protocols, including ISO 15118 vehicle certificates and bidirectional charging.

## 4. Comparing with `@voltbras/ts-ocpp`

`@voltbras/ts-ocpp` is a respected TypeScript-first library that popularized typed OCPP in Node.js.

### Key Strengths
- Clean class-based object-oriented API.
- Strong typing for OCPP 1.6-J messages.
- Established community adoption.

### `ocpp-ws-io` Approach
- **Horizontal Scaling & Clustering**: `ts-ocpp` manages connections in-memory on a single process. Scaling across Kubernetes pods requires developers to build custom pub/sub routing. `ocpp-ws-io` includes an out-of-the-box `RedisAdapter` with O(1) station routing and presence heartbeats.
- **Multi-Protocol Negotiation**: `ocpp-ws-io` provides complete support for OCPP 2.0.1 and OCPP 2.1 alongside 1.6, allowing single servers to negotiate multiple protocols simultaneously.
- **Built-in Rate Limiting**: Built-in token-bucket rate limiters drop rogue station floods (such as high-frequency `MeterValues`) before JSON deserialization.

---

## 5. Comparing with `ocpp-eliftech`

`ocpp-eliftech` is one of the earliest production Node.js OCPP implementations.

### Key Strengths
- Proven track record in early OCPP 1.6-J commercial deployments.
- Simple, unopinionated core.

### `ocpp-ws-io` Approach
- **Modern Protocol Architecture**: `eliftech` is constrained to OCPP 1.6. `ocpp-ws-io` handles 1.6, 2.0.1, and 2.1 with shared connection interfaces.
- **Framework Adapters**: Dedicated adapters for **NestJS**, **Express**, **Fastify**, and **Hono**.
- **Observability**: Seamless integration with `voltlog-io` for structured protocol telemetry.
