## OCPPClient

```typescript
import { OCPPClient } from "ocpp-ws-io";
```

### Constructor

```typescript
const client = new OCPPClient(options: ClientOptions);
```

### Methods

#### `connect()`

Connect to the OCPP server.

```typescript
await client.connect();
```

#### `call(protocol?, method, params, options?)`

Make an RPC call. Throws a `TimeoutError` or protocol-level Error if the request fails.
Make an RPC call. Throws a `TimeoutError` or protocol-level Error if the request fails.

-   `protocol`: Optional. e.g., "ocpp1.6". If omitted, generic type inference is used.
-   `method`: The OCPP method name (e.g., "BootNotification").
-   `params`: The request payload.
-   `options`: `{ timeoutMs?: number, retries?: number, idempotencyKey?: string }`

```typescript
// With manual idempotency key to prevent double execution on reconnections
const result = await client.call("ocpp1.6", "BootNotification", { ... }, { idempotencyKey: "unique-boot-123" });
```

#### `safeCall(protocol?, method, params, options?)`

Exactly like `call()`, except it catches all errors and returns the response payload on success, or `undefined` on error rather than throwing. Useful for fire-and-forget or localized error handling without breaking loops.

```typescript
const result = await client.safeCall(
	"ocpp1.6",
	"ClearCache",
	{},
	{ timeoutMs: 15000 },
);

if (result === undefined) {
	client.logger.warn("Station failed to clear cache", { error });
}
```

#### `handle(protocol?, method, handler)`

Register an RPC handler.

-   `protocol`: Optional. If provided, handler only triggers for this protocol version.
-   `method`: The OCPP method name.
-   `handler`: `(context) => Response | Promise<Response>`

```typescript
// Version specific
client.handle("ocpp1.6", "Reset", ({ params }) => { ... });

// Generic
client.handle("Reset", ({ params }) => { ... });

// Catch-all
client.handle((method, { params }) => { ... });

// OCPP 2.1 SEND message: never answered, ctx.unconfirmed is true
client.handle("NotifyPeriodicEventStream", ({ params, unconfirmed }) => { ... });
```

A handler for an OCPP 2.1 SEND message (such as `NotifyPeriodicEventStream`) is registered the same way. Nothing is sent back for a SEND: the return value is ignored, and a thrown error is logged and emitted as `handlerError`, never sent to the peer.

#### `send(method, params)`

Send an OCPP 2.1 unconfirmed message (RPC type SEND, message type 6). It resolves once the frame is written, because no response exists. It does not wait behind an outstanding `call()`, as the spec allows a SEND at any time. It throws on any protocol other than `ocpp2.1`. Under `strictMode` the payload is validated against the message's schema.

```typescript
await client.send("NotifyPeriodicEventStream", {
  id: 1,
  pending: 0,
  basetime: new Date().toISOString(),
  data: [{ t: 0, v: "230.4" }],
});
```

#### `close(options?)`

Close the connection gracefully or forcefully.

By default, calling `close()` will wait for all pending RPC requests to complete before terminating the socket to prevent interrupting in-flight operations.

```typescript
// Graceful close (waits for pending calls, sends 1000 code)
await client.close({ code: 1000, reason: "Normal Closure" });

// Forceful immediate drop (useful during DDoS or severe errors)
await client.close({ force: true });

// Graceful WS close, but skips waiting for pending asynchronous RPC calls
await client.close({ awaitPending: false });
```

### Properties

#### `logger`

A fully initialized `voltlog-io` instance localized to this client. Automatically includes the client `identity` and `component: "OCPPClient"` in the context of every log message.

```typescript
client.logger.info("Initializing updates", { pendingFiles: 4 });
```

#### Compression

WebSocket compression (RFC 7692 `permessage-deflate`) compresses every message with DEFLATE. It is agreed per connection during the handshake: the client offers it, and it is used only if the server accepts. When either side does not use it, messages go uncompressed and nothing breaks.

| Version | What the spec says |
| --- | --- |
| OCPP 1.6J §5.1 | Allowed as part of WebSocket; no other form of compression recommended |
| OCPP 2.0.1 §3.3 / 2.1 §3.4 | A CSMS SHALL support it. A charging station may; RECOMMENDED on mobile data |

It is **off by default** on the server and on `OCPPClient`, because it costs memory and CPU on every connection, and Node's zlib can fragment memory under high concurrency. Turn it on with `compression: true`, or pass `CompressionOptions` to tune it:

```typescript
// CSMS: accept compression from chargers that offer it (needed for full 2.0.1 / 2.1 compliance)
const server = new OCPPServer({ protocols: ["ocpp2.0.1"], compression: true });

// Charging station on mobile data: offer it to the CSMS
const client = new OCPPClient({ /* … */ compression: { level: 6 } });
```

The defaults keep the cost low: messages under 1 KB (most OCPP traffic, such as `Heartbeat`) are sent uncompressed, and no compression context is kept between messages. `BrowserOCPPClient` has no such option: the browser decides on its own, and all major browsers offer compression.

### Methods

#### `listen(port, host?, options?)`

Start listening on a port. Returns the `http.Server` instance.

#### `auth(handler)`

Attach authentication logic.

```typescript
server.auth((ctx) => {
  // ctx.handshake has .identity, .pathname, .headers, etc.
  ctx.accept({ session: { ... } }); // Attach session data to client
});
```

#### `cors(options)`

Apply CORS rules directly to the server or router levels. This protects endpoints from unauthorized WebSocket hijacking or public IP access.

```typescript
server.cors({
	allowedOrigins: ["https://dashboard.example.com"],
	allowedIPs: ["192.168.1.0/24", "10.0.0.5"],
	allowedSchemes: ["wss"],
});
```

#### `on("client", handler)`

Listen for new connections.

```typescript
server.on("client", (client) => {
	// client is an OCPPServerClient (extends OCPPClient)
	console.log(client.session); // Access session data
});
```

#### `updateTLS(options)`

Hot-reload TLS certificates on all active HTTPS servers without dropping connections.
Only valid when using `SecurityProfile.TLS_BASIC_AUTH` or `TLS_CLIENT_CERT`.

```typescript
server.updateTLS({
	cert: fs.readFileSync("./certs/server.crt"),
	key: fs.readFileSync("./certs/server.key"),
});
```

See [TLS Certificate Hot-Reload](/docs/ocpp-ws-io/security#tls-certificate-hot-reload) for full details.

#### `on("securityEvent", handler)`

Emitted for every security-relevant action. Useful for SIEM, alerting, and audit logging.

```typescript
server.on("securityEvent", (event) => {
	// event.type: "AUTH_FAILED" | "CONNECTION_RATE_LIMIT" | "UPGRADE_ABORTED"
	siem.log(event);
});
```

See [Security Event Monitoring](/docs/ocpp-ws-io/security#security-event-monitoring) for full details.

#### `sendToClient(identity, protocol?, method, params, options?)`

Helper method to dispatch an outgoing RPC call to a specific connected client by its `identity`. Throws an error if the station is not connected. Matches the `client.call()` signature and supports `timeoutMs` in the options argument.

```typescript
const result = await server.sendToClient(
	"CP-001",
	"ocpp1.6",
	"Reset",
	{
		type: "Soft",
	},
	{ timeoutMs: 10000 },
);
```

#### `safeSendToClient(identity, protocol?, method, params, options?)`

Exactly like `sendToClient()`, but catches errors (and disconnected station errors), returning the response payload on success, or `undefined` on error. Highly recommended for bulk operations across your cluster where individual failures shouldn't throw exceptions.

```typescript
const result = await server.safeSendToClient(
	"CP-001",
	"ocpp1.6",
	"UpdateFirmware",
	{ location: "..." },
	{ timeoutMs: 30000 },
);

if (result !== undefined) {
	console.log("Firmware update accepted");
}
```

#### `broadcastBatch(identities, method, params, options?)`

Broadcast an identical RPC call to many stations concurrently. For clustered architectures, unicast commands are grouped and dispatched in pipeline batches via the adapter's streams, reducing per-message TCP round-trip overhead.

```typescript
const targets = ["CP-001", "CP-002", "CP-003", ...thousands];

await server.broadcastBatch(targets, "Reset", { type: "Hard" });
```

#### `stats()`

Returns instantaneous observability metrics about the server's local node status. This is deeply integrated with standard Node.js internals to supply immediate health checks for Prometheus and Loki collection.

```typescript
const telemetry = server.stats();

console.log(`Active Managed Sessions: ${telemetry.activeSessions}`);
console.log(`Active Raw WebSockets: ${telemetry.webSockets?.total}`);
console.log(
	`Pending Network Flushes: ${telemetry.webSockets?.bufferedAmount} bytes`,
);
console.log(`Memory Used: ${telemetry.memoryUsage.heapUsed} bytes`);
console.log(`Uptime: ${telemetry.uptimeSeconds}s`);
console.log(`PID: ${telemetry.pid}`);
```

#### `adapterMetrics()`

Fetches deep backend observability from the underlying clustering adapter. When using the `RedisAdapter`, this returns the `consumerLag` (pending unread stream messages) specific to this node, enabling DevOps to perform accurate horizontal capacity auto-scaling.

```typescript
const metrics = await server.adapterMetrics();
console.log("Redis Backlog:", metrics?.redisConsumerLag?.pendingMessages);
```

## Protocol Constants

### `NOREPLY`

Return `NOREPLY` from a handler to suppress the automatic response. This is useful for asynchronous processing where you might send a response later manually, or for specific OCPP flows.

```typescript
import { NOREPLY } from "ocpp-ws-io";

client.handle("StatusNotification", ({ params }) => {
	// Process the notification but don't send a response immediately
	return NOREPLY;
});
```

### Message types

`MessageType` holds the RPC message type numbers: `CALL` (2), `CALLRESULT` (3), `CALLERROR` (4), and the OCPP 2.1 types `CALLRESULTERROR` (5) and `SEND` (6).

| Received | On `ocpp1.6` / `ocpp2.0.1` | On `ocpp2.1` |
| --- | --- | --- |
| SEND (6) | Unknown type (see below) | Delivered to its handler, never answered |
| CALLRESULTERROR (5) | Unknown type (see below) | `callResultError` event, never answered |
| Any other unknown number | CALLERROR `MessageTypeNotSupported`, ID `"-1"` | CALLERROR `MessageTypeNotSupported`, ID `"-1"` |
| Message ID cannot be read (invalid JSON, not an array, type not a number, ID not a string) | CALLERROR `RpcFrameworkError`, ID `"-1"` | CALLERROR `RpcFrameworkError`, ID `"-1"` |
| Malformed CALL | Answered with CALLERROR | Answered with CALLERROR |
| Malformed or schema-invalid CALLRESULT | Not answered | Answered with CALLRESULTERROR |
| Malformed CALLERROR | Not answered | Not answered |

An unknown message type counts as a bad message (emitting `badMessage`), and it is answered with a CALLERROR `MessageTypeNotSupported` under message ID `"-1"`, since the frame's own ID is not read for a type the protocol does not define. A frame whose message ID cannot be read is answered the same way with `RpcFrameworkError`, as 2.0.1 and 2.1 §4.2.3 require ("When also the MessageId cannot be read, the CALLERROR SHALL contain "-1""). A CALLERROR otherwise only answers a CALL, so two peers cannot loop by answering each other's errors.

A CALL that reuses the message ID of a CALL still being handled is answered with `RpcFrameworkError` on OCPP 2.0.1 and 2.1, and with `GenericError` on OCPP 1.6, whose error-code table has no `RpcFrameworkError`.

The error description of an outgoing CALLERROR or CALLRESULTERROR is cut to 255 characters on OCPP 2.0.1 and 2.1, where `ErrorDescription` is `string[255]`. OCPP 1.6 sets no limit, so descriptions are sent in full there.

### Message IDs

A message ID is a string of at most 36 characters, unique for the sender across reconnects (OCPP-J §4.1.4; 2.0.1 errata 2023-12).

| | Behaviour |
| --- | --- |
| Outgoing CALL / SEND | The per-call `idempotencyKey` if given, else `idGenerator` if set, else a random UUID (36 characters). A call rejects before sending if the ID is empty or already used by a pending call. |
| Incoming CALL / SEND, `idValidator` set | `idValidator` decides, with or without `strictMode`. Returning `false` or throwing rejects the ID. |
| Incoming CALL / SEND, `strictMode` on | IDs over 36 characters are rejected. |
| Incoming CALL / SEND, otherwise | Any string is accepted. |
| ID is not a string | CALLERROR `RpcFrameworkError` under ID `"-1"` (see Message types). |

A rejected CALL is answered under message ID `"-1"` with `RpcFrameworkError` on OCPP 2.0.1 and 2.1, and `GenericError` on OCPP 1.6, whose error-code table has no `RpcFrameworkError`. A rejected SEND is not answered. Both count as bad messages. The browser client has no `strictMode`, so it checks incoming IDs only through `idValidator`.

| `protocols`                 | `string[]`               | `[]`       | OCPP subprotocols to negotiate        |
| `query`                     | `Record<string, string>` | —          | Additional URL query parameters       |
| `reconnect`                 | `boolean`                | `true`     | Auto-reconnect on disconnect          |
| `maxReconnects`             | `number`                 | `Infinity` | Max reconnection attempts             |
| `backoffMin`                | `number`                 | `1000`     | First reconnect delay (ms), doubled after each failed attempt; every wait adds up to 25% at random |
| `backoffMax`                | `number`                 | `30000`    | Where the doubling stops (ms); the random 25% still applies on top |
| `callTimeoutMs`             | `number`                 | `30000`    | Default RPC call timeout (ms)         |
| `callConcurrency`           | `number`                 | `1`        | Max concurrent outbound calls         |
| `maxBadMessages`            | `number`                 | `50`       | Close on the Nth bad message in a row; a valid message resets the count. `0` = zero tolerance, `Infinity` = no limit (logs warning). |
| `badMessageWindowMs`        | `number`                 | —          | Also reset a run of bad messages once it is older than this many ms. |
| `respondWithDetailedErrors` | `boolean`                | `false`    | Include error details in responses    |
| `logging`                   | `LoggingConfig`          | `{}`       | Configuration for structured logging. |

### Methods

All methods match `OCPPClient`:

```typescript
await client.connect();

// Version-aware typed call
const result = await client.call("ocpp1.6", "BootNotification", { ... });
const { success } = await client.safeCall("ocpp1.6", "Heartbeat", {});
const { success } = await client.safeCall("ocpp1.6", "Heartbeat", {});

// Register handlers (version-specific, generic, wildcard)
client.handle("ocpp1.6", "Reset", ({ params }) => { ... });
client.handle("Reset", ({ params }) => { ... });
client.handle((method, { params }) => { ... });

// Close
await client.close();
await client.close({ force: true });
await client.close({ awaitPending: true });

// Runtime reconfiguration
client.reconfigure({ callTimeoutMs: 10000 });

// Handler removal
client.removeHandler("Reset");
client.removeHandler("ocpp1.6", "Reset");
client.removeAllHandlers();

// Raw message
client.sendRaw(JSON.stringify([2, "uuid", "Heartbeat", {}]));
```
