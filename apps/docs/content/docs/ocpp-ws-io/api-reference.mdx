## OCPPClient

```typescript
import { OCPPClient } from "ocpp-ws-io";
```

### Constructor

```typescript
const client = new OCPPClient(options: ClientOptions);
```

The client is typed for its `protocols`: `new OCPPClient({ protocols: ["ocpp1.6"] })` is an `OCPPClient<"ocpp1.6">`, so calls, handlers and responses use the 1.6 types, and a version named in a call must be one of its protocols. Without `protocols`, or with a list only known at runtime, it is typed for every version. Custom protocols declared in `OCPPMethodMap` count as protocols.

A typed client still fits a variable or list typed as plain `OCPPClient`, which is typed for every version, as in 2.x. For a list of clients configured for different protocols that should not make calls typed for the wrong version (for example to close them all), use `AnyOCPPClient`: every client fits it, and it has everything except the calls typed by protocol.

#### ClientOptions

| Option                | Type                            | Default    | Description                                         |
| :-------------------- | :------------------------------ | :--------- | :-------------------------------------------------- |
| `identity`            | `string`                        | _required_ | Charging station ID                                 |
| `endpoint`            | `string`                        | _required_ | WebSocket URL (`ws://` or `wss://`)                 |
| `protocols`           | `string[]`                      | `[]`       | OCPP subprotocols to negotiate                      |
| `securityProfile`     | `SecurityProfile`               | `NONE`     | Security profile (0–3)                              |
| `password`            | `string \| Buffer`              | —          | Password for Basic Auth (Profile 1 & 2)             |
| `tls`                 | `TLSOptions`                    | —          | TLS settings for a `wss://` endpoint, on every security profile (`ca` for a private CA even on profile 0); profile 3 needs `cert` and `key` |
| `headers`             | `Record<string, string>`        | —          | Additional WebSocket headers                        |
| `wsOpts`              | `WsClientOptions`               | —          | Raw `ws` client options: a proxy `agent`, `localAddress`, `family`, `origin`, `maxPayload`, `followRedirects`… (see wsOpts below) |
| `query`               | `Record<string, string> \| string` | —          | URL query parameters, as an object or a query string (`"a=1&b=2"`, leading `?` optional); added after any query in `endpoint` |
| `reconnect`           | `boolean`                       | `true`     | Auto-reconnect on disconnect                        |
| `maxReconnects`       | `number`                        | `Infinity` | Max reconnection attempts                           |
| `pingIntervalMs`      | `number`                        | `30000`    | Includes ±25% randomized jitter                     |
| `strictMode`          | `boolean \| string[]`           | `false`    | Schema validation, off by default. Set `true` (or a list of protocols) for full payload validation (2.0.1 / 2.1 §4.1.7) |
| `strictModeMethods`   | `string[]`                      | —          | Restrict validation to specific methods             |
| `idGenerator`         | `() => string`                  | —          | Creates the message ID of each outgoing CALL and SEND. A per-call `idempotencyKey` wins; without either, a random UUID |
| `idValidator`         | `(id: string) => boolean`       | —          | Checks each incoming CALL / SEND message ID, in any mode, in place of the built-in check (see Message IDs) |
| `logging`             | `LoggingConfig`                 | `{}`       | Configuration for structured logging.               |
| `offlineQueue`        | `boolean`                       | `false`    | Queue calls while disconnected, flush on reconnect. |
| `offlineQueueMaxSize` | `number`                        | `100`      | Max offline queue size before oldest are dropped.   |
| `compression`         | `boolean \| CompressionOptions` | `false`    | Offer WebSocket `permessage-deflate` compression to the CSMS. Off by default: nothing is offered (see Compression) |
| `callConcurrency`     | `number`                        | `1`        | Outbound CALLs in flight at once. `1` follows OCPP-J §4.1.1 (Synchronicity): a new CALL waits until the previous one is answered or has timed out. Above 1 only for a CSMS known to cope (see `callImmediate()`) |
| `respondWithDetailedErrors` | `boolean`                 | `false`    | Send a handler error's properties (not its stack) to the CSMS in CALLERROR `details`. Logs a warning when on; keep it off in production |

#### wsOpts

Passed to `new WebSocket()` from the [`ws`](https://github.com/websockets/ws/blob/master/doc/ws.md#new-websocketaddress-protocols-options) package, for what the client options do not cover. Node client only: a browser's `WebSocket` takes no such options.

```typescript
import { HttpsProxyAgent } from "https-proxy-agent";

const client = new OCPPClient({
  identity: "CP-001",
  endpoint: "wss://csms.example.com/ocpp",
  protocols: ["ocpp1.6"],
  wsOpts: {
    agent: new HttpsProxyAgent("http://proxy.corp.local:3128"), // through a proxy
    localAddress: "192.168.8.20", // leave by this network interface
    maxPayload: 64 * 1024, // refuse messages over 64 KB (the ws default is 100 MiB)
  },
});
```

Its type, `WsClientOptions`, leaves out the options the client sets itself, so they cannot be set in two places:

| Not in `wsOpts` | Use instead |
| :-- | :-- |
| `handshakeTimeout` | `connectTimeoutMs` |
| `perMessageDeflate` | `compression` |
| `headers` | `headers` (names compared without case, as HTTP does; with `password`, its `Authorization` header wins) |
| `ca`, `cert`, `key`, `passphrase`, `rejectUnauthorized`, `minVersion`, `maxVersion`, `ciphers` | `tls`, which applies on every security profile |
| `autoPong` | Nothing: pings are always answered (RFC 6455 §5.5.2), since a CSMS disconnects a charger that stops answering them |

From plain JavaScript, where the type does not apply, these are dropped and a warning names the option to use instead. `closeTimeout` (how long a closing connection waits for the CSMS's close frame; `ws` default 30 s) is accepted although `ws`'s own type definitions do not list it yet.

### Methods

#### `connect()`

Connect to the OCPP server.

```typescript
await client.connect();
```

#### `forProtocol(protocol)`

The same client, typed for one of its protocols, or `undefined` while it speaks another or is not connected. A client configured for several versions is typed for all of them until narrowed this way.

```typescript
const client = new OCPPClient({ identity, endpoint, protocols: ["ocpp1.6", "ocpp2.0.1"] });
await client.connect();

const v16 = client.forProtocol("ocpp1.6");
if (v16) {
  const auth = await v16.call("Authorize", { idTag: "ABC" });
  auth.idTagInfo.status; // the 1.6 response
}
```

#### `call(protocol?, method, params, options?)`

Make an RPC call. Throws a `TimeoutError` or protocol-level Error if the request fails.
Make an RPC call. Throws a `TimeoutError` or protocol-level Error if the request fails.

-   `protocol`: Optional. e.g., "ocpp1.6". If omitted, generic type inference is used.
-   `method`: The OCPP method name (e.g., "BootNotification").
-   `params`: The request payload.
-   `options`: `{ timeoutMs?: number, retries?: number, idempotencyKey?: string, signal?: AbortSignal }`, or `{ noReply: true, … }` (see below)

```typescript
// With manual idempotency key to prevent double execution on reconnections
const result = await client.call("ocpp1.6", "BootNotification", { ... }, { idempotencyKey: "unique-boot-123" });
```

With `{ noReply: true }` (typed `NoReplyCallOptions`), the CALL is sent and `call()` resolves with `undefined` once it is written, without waiting for the answer. The peer still answers, as OCPP-J requires: the answer is recognised by its message ID and dropped quietly while it can still arrive (`timeoutMs`, default `callTimeoutMs`), then the ID is forgotten, so nothing piles up and nothing is logged as a stray response. Unlike a call you do not await, it frees the call queue once it is sent, so the next CALL can go out before this one is answered, which OCPP-J §4.1.1 does not allow: use it only with peers known to cope. `retries` cannot be combined with it. On OCPP 2.1, a message defined as unconfirmed (such as `NotifyPeriodicEventStream`) uses `send()` instead.

```typescript
await client.call("StatusNotification", { connectorId: 1, errorCode: "NoError", status: "Available" }, { noReply: true });
```

#### `safeCall(protocol?, method, params, options?)`

Exactly like `call()`, except it catches all errors and returns the response payload on success, or `undefined` on error rather than throwing. Useful for fire-and-forget or localized error handling without breaking loops.

```typescript
const result = await client.safeCall(
	"ocpp1.6",
	"ClearCache",
	{},
	{ timeoutMs: 15000 },
);

if (result === undefined) {
	client.logger.warn("Station failed to clear cache", { error });
}
```

#### `callImmediate(method, params?, options?)`

Sends a CALL at once, skipping the `callConcurrency` queue, so it can go out while earlier CALLs are still unanswered. That breaks OCPP-J §4.1.1 (Synchronicity): a new CALL waits until the previous one is answered or has timed out, on purpose: use it only with a CSMS known to handle CALLs in parallel, as with `callConcurrency` above 1. Rejects unless the client is connected; there is no offline queue. `server.sendBatch()` uses it.

```typescript
// One StatusNotification per connector after boot, without waiting in turn
await Promise.all([
  client.callImmediate("StatusNotification", { connectorId: 1, errorCode: "NoError", status: "Available" }),
  client.callImmediate("StatusNotification", { connectorId: 2, errorCode: "NoError", status: "Available" }),
]);
```

#### `handle(protocol?, method, handler)`

Register an RPC handler.

-   `protocol`: Optional. If provided, handler only triggers for this protocol version.
-   `method`: The OCPP method name.
-   `handler`: `(context) => Response | Promise<Response>`

```typescript
// Version specific
client.handle("ocpp1.6", "Reset", ({ params }) => { ... });

// Generic
client.handle("Reset", ({ params }) => { ... });

// Catch-all
client.handle((method, { params }) => { ... });

// OCPP 2.1 SEND message: never answered, ctx.unconfirmed is true
client.handle("NotifyPeriodicEventStream", ({ params, unconfirmed }) => { ... });
```

A handler for a SEND message, of OCPP 2.1 (such as `NotifyPeriodicEventStream`) or of a custom protocol, is registered the same way. Nothing is sent back for a SEND: the return value is ignored, and a thrown error is logged and emitted as `handlerError`, never sent to the peer.

#### `send(method, params)`

Send an OCPP 2.1 unconfirmed message (RPC type SEND, message type 6). It resolves once the frame is written, because no response exists. It does not wait behind an outstanding `call()`, as the spec allows a SEND at any time. It works on `ocpp2.1` and on a custom protocol, whose SEND messages you declare in `OCPPSendMethodMap` (`ocpp generate` does), and throws on OCPP 1.6 and 2.0.1, whose RPC framework has no SEND: a peer answers one with `MessageTypeNotSupported`. Under `strictMode` the payload is validated against the message's schema, `$id` `urn:<Message>`.

```typescript
await client.send("NotifyPeriodicEventStream", {
  id: 1,
  pending: 0,
  basetime: new Date().toISOString(),
  data: [{ t: 0, v: "230.4" }],
});
```

#### `close(options?)`

Close the connection gracefully or forcefully.

By default, calling `close()` will wait for all pending RPC requests to complete before terminating the socket to prevent interrupting in-flight operations.

```typescript
// Graceful close (waits for pending calls, sends 1000 code)
await client.close({ code: 1000, reason: "Normal Closure" });

// Forceful immediate drop (useful during DDoS or severe errors)
await client.close({ force: true });

// Graceful WS close, but skips waiting for pending asynchronous RPC calls
await client.close({ awaitPending: false });
```

### Properties

#### `logger`

A fully initialized `voltlog-io` instance localized to this client. Automatically includes the client `identity` and `component: "OCPPClient"` in the context of every log message.

```typescript
client.logger.info("Initializing updates", { pendingFiles: 4 });
```

## OCPPServer

```typescript
import { OCPPServer } from "ocpp-ws-io";
```

### Constructor

```typescript
const server = new OCPPServer(options?: ServerOptions);
```

The server is typed for its `protocols`, like the client: `new OCPPServer({ protocols: ["ocpp1.6"] })` is an `OCPPServer<"ocpp1.6">`. Its connections (the `client` event, `getLocalClient()`, `clients`) are `OCPPServerClient<"ocpp1.6">`, and its routes and their handlers, `ctx.accept({ protocol })`, `sendToClient()`, `broadcast()` and inline plugins take only its versions. A route's `config({ protocols })` must be a subset of the server's. Without `protocols`, or with a list only known at runtime, the server is typed for every version.

A typed server, route or connection still fits a variable or list typed as plain `OCPPServer`, `OCPPRouter` or `OCPPServerClient`, typed for every version as in 2.x. To keep the exact type, use `ConnectionOf<typeof server>`; for connections of differently configured servers that should not make calls typed for the wrong version, `AnyOCPPServerClient`. On a server with several versions, `client.forProtocol("ocpp1.6")` returns the connection typed for the version it negotiated, or `undefined`:

```typescript
import { type ConnectionOf, OCPPServer } from "ocpp-ws-io";

const server = new OCPPServer({ protocols: ["ocpp1.6", "ocpp2.0.1"] });
const connections = new Map<string, ConnectionOf<typeof server>>();

server.on("client", (client) => {
  connections.set(client.identity, client);
  client.forProtocol("ocpp1.6")?.handle("Authorize", () => ({
    idTagInfo: { status: "Accepted" }, // the 1.6 response
  }));
});
```

#### wssOptions

Passed to `new WebSocketServer()` from the [`ws`](https://github.com/websockets/ws/blob/master/doc/ws.md#new-websocketserveroptions-callback) package, for what the server options do not cover. Changes through `reconfigure()` apply to new connections.

```typescript
const server = new OCPPServer({
  protocols: ["ocpp2.0.1"],
  wssOptions: {
    maxFragments: 64, // close (1008) on a message split into more fragments
    maxBufferedChunks: 4096, // the same for buffered chunks of one message
    closeTimeout: 5_000, // destroy a closing socket after 5 s without the charger's close frame
  },
});
```

| Option | `ws` default | Use |
| :-- | :-- | :-- |
| `maxFragments`, `maxBufferedChunks` | 16384, 262144 | Lower them on a server exposed to the internet: limits against fragment floods |
| `allowSynchronousEvents` | `true` | `false` spreads a burst of messages from one charger over several event-loop turns |
| `skipUTF8Validation` | `false` | Faster parsing, but invalid UTF-8 then reaches the parser instead of closing the connection with 1007 as RFC 6455 requires |
| `WebSocket` | `ws`'s `WebSocket` | A subclass, e.g. for instrumentation |
| `closeTimeout` | 30000 | How long a closing connection waits for the charger's close frame; accepted although `ws`'s type definitions do not list it yet |

Its type, `WsServerOptions`, leaves out the options the server sets itself:

| Not in `wssOptions` | Use instead |
| :-- | :-- |
| `port`, `host`, `server`, `noServer`, `backlog` | `listen(port, host, { server })` or `handleUpgrade`; `backlog` on your own HTTP server |
| `path` | `route()` |
| `handleProtocols` | `protocols` |
| `verifyClient` | `auth()`, middleware or `isKnownIdentity` |
| `maxPayload` | `maxPayloadBytes` |
| `perMessageDeflate` | `compression` |
| `clientTracking` | Nothing: always on, `stats()` needs it |
| `autoPong` | Nothing: charger pings are always answered (RFC 6455 §5.5.2) |

From plain JavaScript, where the type does not apply, these are dropped and a warning names what to use instead.

#### Compression

WebSocket compression (RFC 7692 `permessage-deflate`) compresses every message with DEFLATE. It is agreed per connection during the handshake: the client offers it, and it is used only if the server accepts. When either side does not use it, messages go uncompressed and nothing breaks.

| Version | What the spec says |
| --- | --- |
| OCPP 1.6J §5.1 | Allowed as part of WebSocket; no other form of compression recommended |
| OCPP 2.0.1 §3.3 / 2.1 §3.4 | A CSMS SHALL support it. A charging station may; RECOMMENDED on mobile data |

It is **off by default** on the server and on `OCPPClient`, because it costs memory and CPU on every connection, and Node's zlib can fragment memory under high concurrency. Turn it on with `compression: true`, or pass `CompressionOptions` to tune it:

```typescript
// CSMS: accept compression from chargers that offer it (needed for full 2.0.1 / 2.1 compliance)
const server = new OCPPServer({ protocols: ["ocpp2.0.1"], compression: true });

// Charging station on mobile data: offer it to the CSMS
const client = new OCPPClient({ /* … */ compression: { level: 6 } });
```

The defaults keep the cost low: messages under 1 KB (most OCPP traffic, such as `Heartbeat`) are sent uncompressed, and no compression context is kept between messages. `BrowserOCPPClient` has no such option: the browser decides on its own, and all major browsers offer compression.

### Methods

#### `listen(port, host?, options?)`

Start listening on a port. Returns the `http.Server` instance.

#### `auth(handler)`

Attach authentication logic.

```typescript
server.auth((ctx) => {
  // ctx.handshake has .identity, .pathname, .headers, etc.
  ctx.accept({ session: { ... } }); // Attach session data to client
});
```

On a typed server, `ctx.accept({ protocol })` takes only its protocols. Callbacks from `defineAuth()` or `combineAuth()`, or typed `AuthCallback`, fit any server; written inline in `auth()`, they take that server's protocols.

	allowedSchemes: ["wss"],

#### `sendToClient(identity, protocol?, method, params, options?)`

Helper method to dispatch an outgoing RPC call to a specific connected client by its `identity`. Throws an error if the station is not connected. Matches the `client.call()` signature and supports `timeoutMs` in the options argument.

```typescript
const result = await server.sendToClient(
	"CP-001",
	"ocpp1.6",
	"Reset",
	{
		type: "Soft",
	},
	{ timeoutMs: 10000 },
);
```

#### `safeSendToClient(identity, protocol?, method, params, options?)`

Exactly like `sendToClient()`, but catches errors (and disconnected station errors), returning the response payload on success, or `undefined` on error. Highly recommended for bulk operations across your cluster where individual failures shouldn't throw exceptions.

```typescript
const result = await server.safeSendToClient(
	"CP-001",
	"ocpp1.6",
	"UpdateFirmware",
	{ location: "..." },
	{ timeoutMs: 30000 },
);

if (result !== undefined) {
	console.log("Firmware update accepted");
}
```

#### `sendBatch(identity, calls)`

Sends several CALLs to one charger **without waiting for each answer**, for a faster warm-up after a reconnect. This pipelines on purpose and breaks OCPP-J §4.1.1 (Synchronicity): a new CALL waits until the previous one is answered or has timed out: use it only with chargers known to cope, as with `callConcurrency` above 1. Results come back in the order of `calls`; a call that failed gives `undefined`. In a cluster, a charger connected to another node gets each call through `sendToClient()` instead.

```typescript
const [config, , trigger] = await server.sendBatch("CP-101", [
  { method: "GetConfiguration", params: { key: ["MeterValueSampleInterval"] } },
  { method: "ChangeAvailability", params: { connectorId: 0, type: "Operative" } },
  { method: "TriggerMessage", params: { requestedMessage: "StatusNotification" } },
]);
```

Each call is typed by its `method`, and the results by their actions. A call to an action the types do not know takes `unchecked()`: `{ method: unchecked("VendorPing"), params: { n: 1 } }`.

#### `broadcastBatch(identities, method, params, options?)`

Broadcast an identical RPC call to many stations concurrently. For clustered architectures, unicast commands are grouped and dispatched in pipeline batches via the adapter's streams, reducing per-message TCP round-trip overhead.

```typescript
const targets = ["CP-001", "CP-002", "CP-003", ...thousands];

await server.broadcastBatch(targets, "Reset", { type: "Hard" });
```

## Protocol Constants

### `NOREPLY`

Return `NOREPLY` from a handler to suppress the automatic response. This is useful for asynchronous processing where you might send a response later manually, or for specific OCPP flows.

```typescript
import { NOREPLY } from "ocpp-ws-io";

client.handle("StatusNotification", ({ params }) => {
	// Process the notification but don't send a response immediately
	return NOREPLY;
});
```

An async handler can return it too, after its work:

```typescript
client.handle("StatusNotification", async ({ params }) => {
	await queue.push(params);
	return NOREPLY;
});
```

### `unchecked(action)`

Marks an action name the types do not check, for every typed method (`call`, `safeCall`, `callImmediate`, `handle`, `send`, `removeHandler`, `sendToClient`, `safeSendToClient`, `broadcast`, `broadcastBatch`, and a `sendBatch` call's `method`): an undeclared vendor action, a name passed through from the wire, or a test that sends an invalid payload on purpose. Returns the name unchanged.

```typescript
import { unchecked } from "ocpp-ws-io";

const res = await client.call(unchecked("VendorPing"), { n: 1 }); // a JSON object
client.handle(unchecked("VendorPing"), () => ({ pong: true }));
```

Typed methods otherwise take only the actions their protocols define, and reject keys the OCPP schema does not define; see [Type Safety](/docs/ocpp-ws-io/type-safety).

### Message types

`MessageType` holds the RPC message type numbers: `CALL` (2), `CALLRESULT` (3), `CALLERROR` (4), and the OCPP 2.1 types `CALLRESULTERROR` (5) and `SEND` (6).

| Received | On `ocpp1.6` / `ocpp2.0.1` | On `ocpp2.1` |
| --- | --- | --- |
| SEND (6) | Unknown type (see below) | Delivered to its handler, never answered |
| CALLRESULTERROR (5) | Unknown type (see below) | `callResultError` event, never answered |
| Any other unknown number | CALLERROR `MessageTypeNotSupported`, ID `"-1"` | CALLERROR `MessageTypeNotSupported`, ID `"-1"` |
| Message ID cannot be read (invalid JSON, not an array, type not a number, ID not a string) | CALLERROR `RpcFrameworkError`, ID `"-1"` | CALLERROR `RpcFrameworkError`, ID `"-1"` |
| Malformed CALL | Answered with CALLERROR | Answered with CALLERROR |
| Malformed or schema-invalid CALLRESULT | Not answered | Answered with CALLRESULTERROR |
| Malformed CALLERROR | Not answered | Not answered |

An unknown message type counts as a bad message (emitting `badMessage`), and it is answered with a CALLERROR `MessageTypeNotSupported` under message ID `"-1"`, since the frame's own ID is not read for a type the protocol does not define. A frame whose message ID cannot be read is answered the same way with `RpcFrameworkError`, as 2.0.1 and 2.1 §4.2.3 require ("When also the MessageId cannot be read, the CALLERROR SHALL contain "-1""). A CALLERROR otherwise only answers a CALL, so two peers cannot loop by answering each other's errors.

A CALL that reuses the message ID of a CALL still being handled is answered with `RpcFrameworkError` on OCPP 2.0.1 and 2.1, and with `GenericError` on OCPP 1.6, whose error-code table has no `RpcFrameworkError`.

The error description of an outgoing CALLERROR or CALLRESULTERROR is cut to 255 characters on OCPP 2.0.1 and 2.1, where `ErrorDescription` is `string[255]`. OCPP 1.6 sets no limit, so descriptions are sent in full there.

### Message IDs

A message ID is a string of at most 36 characters, unique for the sender across reconnects (OCPP-J §4.1.4; 2.0.1 errata 2023-12).

| | Behaviour |
| --- | --- |
| Outgoing CALL / SEND | The per-call `idempotencyKey` if given, else `idGenerator` if set, else a random UUID (36 characters). A call rejects before sending if the ID is empty or already used by a pending call. |
| Incoming CALL / SEND, `idValidator` set | `idValidator` decides, with or without `strictMode`. Returning `false` or throwing rejects the ID. |
| Incoming CALL / SEND, `strictMode` on | IDs over 36 characters are rejected. |
| Incoming CALL / SEND, otherwise | Any string is accepted. |
| ID is not a string | CALLERROR `RpcFrameworkError` under ID `"-1"` (see Message types). |

A rejected CALL is answered under message ID `"-1"` with `RpcFrameworkError` on OCPP 2.0.1 and 2.1, and `GenericError` on OCPP 1.6, whose error-code table has no `RpcFrameworkError`. A rejected SEND is not answered. Both count as bad messages. The browser client has no `strictMode`, so it checks incoming IDs only through `idValidator`.

#### BrowserClientOptions

| Option                      | Type                     | Default    | Description                           |
| :-------------------------- | :----------------------- | :--------- | :------------------------------------ |
| `identity`                  | `string`                 | _required_ | Charging station ID                   |
| `endpoint`                  | `string`                 | _required_ | WebSocket URL (`ws://` or `wss://`)   |

| `logging`                   | `LoggingConfig`          | `{}`       | Configuration for structured logging. |
